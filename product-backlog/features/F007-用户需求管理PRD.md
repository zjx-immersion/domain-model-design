## 一、特性概述

### 1.1 背景

在Auto DevOps平台中，用户需求是整个研发流程的起点。当前面临的问题：
- 需求来自多个渠道（整车、干系人、市场），缺乏统一管理
- 需求信息不完整，缺少上下文和追溯
- 需求优先级不清晰，资源分配困难
- 需求评审流程不规范
- 需求与实现脱节，难以追溯

### 1.2 目标

**业务目标**:
- 统一管理所有用户需求
- 建立规范的需求评审流程
- 支持需求优先级管理
- 实现需求的全程可追溯

**用户目标**:
- 产品经理: 高效管理和分析需求
- 系统工程师: 清晰理解需求来源和上下文
- 团队成员: 追溯需求背景和决策依据

### 1.3 核心价值

```
对产品经理:
├─ 统一的需求管理入口
├─ 结构化的需求信息
├─ 规范的评审流程
└─ 数据驱动的优先级决策

对系统工程师:
├─ 清晰的需求来源和上下文
├─ 完整的需求评审材料
├─ 需求的可追溯性
└─ 需求分解的基础

对团队:
├─ 透明的需求状态
├─ 明确的优先级
└─ 清晰的验收标准
```

### 1.4 范围

**包含**:
- 用户需求的CRUD操作
- 需求来源和干系人管理
- 需求优先级和分类
- 需求评审流程
- 需求基础分解功能
- 需求状态跟踪

**不包含**:
- 特性需求的详细管理（由F008负责）
- 需求变更管理（由F011负责）
- 需求分析的AI辅助（V2.0）

## 二、用户画像与场景

### 2.1 用户画像

#### 主要用户: 领域产品经理

**基本信息**:
- 角色: 领域产品经理

**使用场景**:
- 每天: 查看和处理新需求 3-5个
- 每周: 需求评审会议 2-3次
- 每月: 需求优先级评估和调整

#### 次要用户: 系统工程师

**基本信息**:
- 角色: 系统工程师
- 经验: 3-8年技术经验
- 技能: 系统设计、需求分析
- 痛点: 需求不清晰、上下文缺失、评审材料不全

**使用场景**:
- 每天: 查看待评审需求 2-3个
- 每周: 参与需求评审 2-3次
- 每月: 需求技术可行性分析 5-8个

### 2.2 典型场景

#### 场景1: 创建用户需求

**场景描述**:
理想汽车产品经理收到整车团队的需求："新车型L7需要支持NOA自动驾驶功能"

**前置条件**:
- 用户已登录系统
- 用户有创建需求的权限

**操作流程**:
1. 产品经理进入"用户需求管理"模块
2. 点击"创建需求"按钮
3. 填写需求信息:
   - 标题: "L7车型支持NOA自动驾驶功能"
   - 来源: 整车需求
   - 描述: 详细的需求内容
   - 目标产品: NOA领域产品
   - 优先级: 高
   - 干系人: 整车产品经理、L7项目经理
4. 上传附件（需求文档、会议纪要）
5. 点击"保存"
6. 系统自动分配需求编号（UR-NOA-001）
7. 系统自动通知相关干系人

**后置条件**:
- 需求记录创建成功
- 需求状态为"草稿"
- 相关人员收到通知

**价值体现**:
- 需求信息完整记录
- 需求来源清晰可追溯
- 干系人及时知晓

---

#### 场景2: 需求评审

**场景描述**:
产品经理创建需求后，发起评审，系统工程师评估技术可行性

**前置条件**:
- 需求已创建（状态为"草稿"）
- 有评审人权限的用户

**操作流程（产品经理）**:
1. 打开需求详情页
2. 点击"发起评审"按钮
3. 选择评审人（系统工程师、架构师）
4. 填写评审要点
5. 设置评审期限
6. 提交评审申请
7. 需求状态变更为"评审中"

**操作流程（系统工程师）**:
1. 收到评审通知
2. 进入需求详情页查看
3. 分析需求内容
4. 在资产库搜索可复用资产
5. 填写评审意见:
   - 技术可行性: 可行
   - 建议方案: 复用L9 NOA资产，适配J6M平台
   - 工作量估算: 80人天
   - 风险识别: 平台适配风险
6. 提交评审结果: 通过

**操作流程（产品经理确认）**:
1. 收到评审完成通知
2. 查看评审意见
3. 确认需求
4. 需求状态变更为"已确认"

**后置条件**:
- 需求评审完成
- 评审意见记录
- 需求可以进入分解阶段

**价值体现**:
- 规范的评审流程
- 技术可行性验证
- 工作量预估
- 风险提前识别

---

#### 场景3: 需求分解

**场景描述**:
系统工程师将用户需求分解为特性需求

**前置条件**:
- 需求状态为"已确认"
- 用户有需求分解权限

**操作流程**:
1. 系统工程师打开需求详情
2. 点击"分解需求"按钮
3. 系统显示分解向导
4. 系统工程师创建特性需求:
   - 特性需求1: "融合感知功能"
   - 特性需求2: "路径规划功能"
   - 特性需求3: "车辆控制功能"
5. 系统自动建立追溯关系
6. 分配特性需求给特性负责人
7. 提交分解结果

**后置条件**:
- 创建3个特性需求
- 建立追溯关系 (UR-NOA-001 → FR-NOA-001, FR-NOA-002, FR-NOA-003)
- 特性负责人收到通知
- 需求状态变更为"已分解"

**价值体现**:
- 需求逐层分解
- 追溯关系自动建立
- 责任明确到人

## 三、功能需求

### 3.1 需求管理

#### 3.1.1 创建需求 [Must Have]

**功能描述**: 产品经理创建新的用户需求

**输入**:
- 需求标题（必填，最多200字）
- 需求来源（必选）:
  - 整车需求
  - 干系人需求
  - 市场需求
  - 技术需求
- 需求描述（必填，富文本）
- 需求背景（选填）
- 目标资产（选填）:
  - 目标产品
  - 目标特性
- 需求类型（必选）:
  - 功能需求
  - 性能需求
  - 合规需求
  - 其他
- 优先级（必选）:
  - P0 - 紧急
  - P1 - 高
  - P2 - 中
  - P3 - 低
- 强制级别（必选）:
  - 必须
  - 应该
  - 可以
- 干系人（选填，多选）
- 附件（选填，支持多个）

**输出**:
- 需求记录
- 需求编号（自动生成）
- 创建时间
- 创建人

**业务规则**:
- 需求编号格式: UR-{产品代码}-{序号}
- 新创建的需求默认状态为"草稿"
- 自动通知选中的干系人

#### 3.1.2 编辑需求 [Must Have]

**功能描述**: 修改需求信息

**权限**:
- 需求创建人
- 产品经理角色

**限制**:
- 需求状态为"草稿"或"已退回"时可编辑所有字段
- 需求状态为"评审中"时不可编辑
- 需求状态为"已确认"后只可编辑描述和附件，其他变更需走变更流程

#### 3.1.3 查看需求 [Must Have]

**功能描述**: 查看需求详情

**展示内容**:
- 基本信息（标题、编号、状态、优先级等）
- 需求描述
- 来源信息
- 目标资产
- 干系人列表
- 附件列表
- 追溯关系（关联的特性需求）
- 评审记录
- 变更历史
- 操作日志

#### 3.1.4 删除需求 [Could Have]

**功能描述**: 删除需求记录

**权限**: 产品经理

**限制**:
- 只能删除"草稿"状态的需求
- 已有追溯关系的需求不可删除
- 删除操作记录日志

### 3.2 需求评审

#### 3.2.1 发起评审 [Must Have]

**功能描述**: 产品经理发起需求评审

**前置条件**:
- 需求状态为"草稿"
- 需求信息完整

**输入**:
- 评审人（必选，多选）
- 评审期限（必选）
- 评审要点（选填）

**输出**:
- 评审申请记录
- 需求状态变更为"评审中"
- 评审通知发送

#### 3.2.2 执行评审 [Must Have]

**功能描述**: 评审人评审需求

**输入**:
- 技术可行性（必选）:
  - 可行
  - 有风险但可行
  - 不可行
- 建议方案（必填）
- 工作量估算（选填，人天）
- 风险识别（选填）
- 评审意见（必填）
- 评审结果（必选）:
  - 通过
  - 有条件通过
  - 不通过

**输出**:
- 评审记录
- 评审通知（通知需求创建人）

**业务规则**:
- 所有评审人都提交后，评审完成
- 任一评审人"不通过"，整体评审结果为"不通过"

#### 3.2.3 确认评审结果 [Must Have]

**功能描述**: 产品经理确认评审结果

**操作**:
- 查看评审意见
- 确认需求: 状态变更为"已确认"
- 退回修改: 状态变更为"已退回"

### 3.3 需求分解

#### 3.3.1 基础分解 [Must Have]

**功能描述**: 系统工程师将用户需求分解为特性需求

**前置条件**:
- 需求状态为"已确认"

**操作流程**:
1. 点击"分解需求"
2. 创建特性需求（跳转到特性需求创建页面）
3. 系统自动关联用户需求
4. 系统自动建立追溯关系

**输出**:
- 特性需求记录
- 追溯关系记录
- 用户需求状态变更为"已分解"

#### 3.3.2 分解验证 [Should Have]

**功能描述**: 验证需求分解的完整性

**验证规则**:
- 至少有一个特性需求
- 所有特性需求都关联了具体特性
- 特性需求覆盖了用户需求的所有功能点

### 3.4 需求跟踪

#### 3.4.1 状态跟踪 [Must Have]

**需求状态流转**:
```
草稿 → 评审中 → 已确认 → 已分解 → 开发中 → 已实现 → 已验证 → 已关闭
   ↓      ↓
 已退回  已退回
```

**状态说明**:
- 草稿: 初始状态
- 评审中: 正在评审
- 已退回: 评审不通过，需修改
- 已确认: 评审通过
- 已分解: 已分解为特性需求
- 开发中: 关联的特性需求进入开发
- 已实现: 所有特性需求开发完成
- 已验证: 需求验证通过
- 已关闭: 需求完成并关闭

#### 3.4.2 进度跟踪 [Must Have]

**功能描述**: 查看需求的实现进度

**展示内容**:
- 关联的特性需求列表
- 每个特性需求的状态
- 整体进度百分比
- 关键里程碑

### 3.5 需求检索

#### 3.5.1 列表查询 [Must Have]

**功能描述**: 查询需求列表

**查询条件**:
- 关键词搜索（标题、描述）
- 状态过滤（多选）
- 优先级过滤（多选）
- 来源过滤
- 创建人过滤
- 创建时间范围
- 目标产品过滤

**排序**:
- 创建时间（默认降序）
- 优先级
- 更新时间

**展示字段**:
- 需求编号
- 标题
- 状态
- 优先级
- 来源
- 创建人
- 创建时间
- 操作（查看、编辑、删除）

#### 3.5.2 高级搜索 [Should Have]

**功能描述**: 提供更丰富的搜索条件

**额外条件**:
- 干系人
- 目标特性
- 标签
- 评审人
- 评审结果

## 八、技术方案

### 8.1 数据模型

```typescript
// 用户需求实体
interface UserRequirement {
  id: string;                    // 需求ID
  code: string;                  // 需求编号 UR-XXX-001
  title: string;                 // 标题
  source: {                      // 来源
    type: RequirementSourceType; // 整车需求/干系人需求/市场需求/技术需求
    description: string;         // 来源描述
    reference: string;           // 参考编号
  };
  description: string;           // 需求描述（富文本）
  rationale: string;             // 需求背景
  type: RequirementType;         // 需求类型
  priority: Priority;            // 优先级
  mandatoryLevel: MandatoryLevel; // 强制级别
  targetAsset: {                 // 目标资产
    productId: string;           // 目标产品
    featureId?: string;          // 目标特性
  };
  stakeholders: Stakeholder[];   // 干系人
  attachments: Attachment[];     // 附件
  acceptanceCriteria: string[];  // 验收标准
  constraints: Constraint[];     // 约束条件
  status: RequirementStatus;     // 状态
  createdBy: string;             // 创建人
  createdDate: Date;             // 创建时间
  approvedDate?: Date;           // 批准时间
  implementedDate?: Date;        // 实现时间
  // 关联关系
  featureRequirements: string[]; // 关联的特性需求
  reviews: Review[];             // 评审记录
  changeHistory: Change[];       // 变更历史
}

// 评审记录
interface Review {
  id: string;
  reviewers: Reviewer[];         // 评审人
  deadline: Date;                // 评审期限
  reviewPoints: string[];        // 评审要点
  status: ReviewStatus;          // 评审状态
  submittedDate?: Date;          // 提交时间
  completedDate?: Date;          // 完成时间
}

// 评审人意见
interface Reviewer {
  userId: string;
  feasibility: Feasibility;      // 技术可行性
  suggestedApproach: string;     // 建议方案
  effortEstimate?: number;       // 工作量估算
  risks: Risk[];                 // 风险识别
  opinion: string;               // 评审意见
  result: ReviewResult;          // 评审结果
  submittedDate?: Date;
}
```

### 8.2 API设计

```typescript
// 创建用户需求
POST /api/v1/requirements/user
Request: UserRequirement
Response: UserRequirement

// 获取需求列表
GET /api/v1/requirements/user
Query: {
  keyword?: string;
  status?: RequirementStatus[];
  priority?: Priority[];
  source?: RequirementSourceType[];
  createdBy?: string;
  createdDateFrom?: Date;
  createdDateTo?: Date;
  page: number;
  pageSize: number;
}
Response: {
  items: UserRequirement[];
  total: number;
  page: number;
  pageSize: number;
}

// 获取需求详情
GET /api/v1/requirements/user/:id
Response: UserRequirement

// 更新用户需求
PUT /api/v1/requirements/user/:id
Request: Partial<UserRequirement>
Response: UserRequirement

// 删除用户需求
DELETE /api/v1/requirements/user/:id
Response: { success: boolean }

// 发起需求评审
POST /api/v1/requirements/user/:id/review
Request: {
  reviewers: string[];
  deadline: Date;
  reviewPoints: string[];
}
Response: Review

// 提交评审意见
POST /api/v1/requirements/user/:id/review/:reviewId/submit
Request: Reviewer
Response: Review

// 确认评审结果
POST /api/v1/requirements/user/:id/review/:reviewId/confirm
Request: {
  action: 'approve' | 'reject';
}
Response: UserRequirement

// 分解需求
POST /api/v1/requirements/user/:id/decompose
Request: {
  featureRequirements: string[]; // 特性需求ID列表
}
Response: {
  traces: TraceLink[];
}
```
