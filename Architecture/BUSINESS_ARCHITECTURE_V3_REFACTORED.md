# Auto DevOps平台 - 业务架构设计 v3.0（重构版）

> **文档版本**: v3.0  
> **创建日期**: 2025-01-05  
> **重构原因**: 简化需求到任务的转换流程，支持多种工作项类型  
> **重大变更**: 取消Story层，引入Work Item统一管理体系

---

## 📋 v3.0 重大变更说明

### 核心架构变更

#### 1. 简化需求层级 ⭐⭐⭐

**旧架构**:
```
用户需求 → 特性需求 → 模块需求 → Story → Task
（5层，过于复杂）
```

**新架构**:
```
用户需求 → 特性需求 → 模块需求 → Task
（4层，直接转换）
```

**变更理由**:
- Story层主要用于敏捷开发，但模块需求已经足够细化
- 减少管理层级，提升效率
- 降低学习成本和使用复杂度

#### 2. 引入工作项（Work Item）统一管理体系 ⭐⭐⭐

**工作项类型**:
```typescript
type WorkItemType = 
  | 'module_requirement'  // 模块需求
  | 'bugfix'              // 缺陷修复
  | 'tech_debt'           // 技术债
  | 'non_functional'      // 非功能需求（性能、安全等）
  | 'optimization'        // 优化改进
  | 'research'            // 技术调研
```

**工作项流转**:
```
工作项（任意类型） → 拆分为Task → 分配到Sprint → 团队执行
```

**变更理由**:
- 支持多种工作类型，不仅仅是需求
- Bugfix、技术债可以直接进入迭代，不需要"伪装"成需求
- 统一的工作项管理界面，提升管理效率

#### 3. 明确团队-模块责任绑定 ⭐⭐

**团队模型**:
```
团队 → 负责1-n个模块 → 接收相关的工作项
```

**PI Planning流程**:
```
1. 收集所有工作项（需求、Bugfix、技术债等）
2. 根据工作项涉及的模块 → 自动分配到对应团队
3. 团队拆分工作项为Task
4. 按优先级和产能分配到Sprint
```

**变更理由**:
- 明确团队责任范围
- 自动化工作项分配
- 减少协调成本

### 3.2 工作项自动分配逻辑

```python
def assign_work_item_to_team(work_item):
    """根据工作项涉及的模块，自动分配到对应团队"""
    
    # 1. 获取工作项关联的模块
    module_id = work_item.module_id
    
    # 2. 查找负责该模块的团队
    team = find_team_by_module(module_id)
    
    # 3. 检查团队产能
    if team.has_capacity():
        # 分配到团队
        work_item.assigned_team_id = team.id
        return team
    else:
        # 产能不足，标记为待分配
        work_item.status = 'pending_assignment'
        return None
```

### 3.3 跨团队工作项处理

对于涉及多个模块的工作项：

```
策略1: 主责团队
- 识别主要涉及的模块
- 分配给主责团队
- 其他团队作为协同方

策略2: 工作项拆分
- 按模块拆分为多个子工作项
- 分别分配给对应团队
- 识别依赖关系

策略3: 虚拟团队
- 组建临时跨团队
- 专门处理跨模块工作项
```

## 五、简化的需求追溯体系

### 5.1 新的追溯层级

**旧的7层追溯**（过于复杂）:
```
战略目标 → 产品路线图 → 用户需求 → 特性需求 → 模块需求 → Story → Task
```

**新的6层追溯**（简化高效）:
```
战略目标 → 产品路线图 → 用户需求 → 特性需求 → 模块需求 → Task
```

**进一步的端到端追溯**:
```
模块需求 → 工作项 → Task → Commit → PR → 测试用例 → 缺陷 → 构建 → 发布
```

### 5.2 追溯关系示例

```
用户需求: UR-001 "高速NOA自动换道优化"
    ↓
特性需求: FR-001 "融合感知优化"
          FR-002 "决策规划增强"
    ↓
模块需求: MR-001 "感知融合算法优化"
          MR-002 "障碍物检测增强"
          MR-003 "换道决策优化"
    ↓
工作项:   WI-001 "感知融合算法优化" (模块需求类型)
          WI-002 "内存泄漏修复" (Bugfix类型)
          WI-003 "代码重构" (技术债类型)
    ↓
任务:     TASK-001 "算法模型优化"
          TASK-002 "性能测试"
          TASK-003 "文档更新"
    ↓
代码:     COMMIT-001 "feat: 优化感知融合算法"
          PR-001 "融合感知算法优化"
    ↓

          DEFECT-001 "边界条件异常"
    ↓
发布:     BUILD-001 → RELEASE-001 (v3.1.0)
```

#### 1. 工作项（Work Item）- 新增核心实体

```typescript
interface WorkItem {
  // 基本信息
  id: string;
  type: WorkItemType;            // 工作项类型
  title: string;
  description: string;
  priority: 'P0' | 'P1' | 'P2' | 'P3';
  status: WorkItemStatus;
  
  // 来源关联
  sourceType: 'requirement' | 'defect' | 'tech_debt' | 'nfr' | 'optimization' | 'research';
  sourceId?: string;             // 来源实体ID
  moduleId?: string;             // 关联的模块
  requirementId?: string;        // 关联的需求（如果是需求类）
  defectId?: string;             // 关联的缺陷（如果是Bugfix）
  
  // 分配信息
  assignedTeamId?: string;       // 分配的团队
  assignedSprintId?: string;     // 分配的Sprint
  
  // 工作量
  estimatedEffort: number;       // 估算工作量（小时或SP）
  actualEffort?: number;         // 实际工作量
  
  // 任务拆分
  tasks: string[];               // 拆分的Task ID列表
  taskCount: number;             // 任务数量
  completedTaskCount: number;    // 完成的任务数量
  
  // 依赖和阻塞
  dependencies: string[];        // 依赖的工作项
  blockedBy: string[];           // 被哪些工作项阻塞
  
  // 元数据
  createdBy: string;
  createdAt: string;
  updatedAt: string;
  completedAt?: string;
}

type WorkItemType = 
  | 'module_requirement'   // 模块需求
  | 'bugfix'               // 缺陷修复
  | 'tech_debt'            // 技术债
  | 'non_functional'       // 非功能需求
  | 'optimization'         // 优化改进
  | 'research';            // 技术调研

type WorkItemStatus = 
  | 'backlog'       // 待办
  | 'planned'       // 已规划
  | 'in_progress'   // 进行中
  | 'completed'     // 已完成
  | 'cancelled';    // 已取消
```
